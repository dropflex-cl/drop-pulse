# Modelo físico objetivo y mapping

**Modelo objetivo, parcialmente implementado en local.** [ADR 009](adrs/009-persistent-product-context.md) describe las tablas/RPC efectivas de contexto y sus límites; el grafo y la estrategia ya están persistidos según [ADR 010](adrs/010-persistent-knowledge-and-strategy.md). Ejecución/jobs y algunas extensiones del mapping siguen pendientes. Dirección vigente: [approach del chat](approach-chat-first.md) y [ADR 006](adrs/006-chat-first-optimization.md). El contrato MCP define el modelo canónico; no se migra análisis legacy ni se conservan sus writers en el objetivo final. PostgreSQL/Supabase existentes; tipos y keys persistidas en inglés; actor y tenant fuera de argumentos del modelo. Referencias E*: [auditoría](audit-current-model.md#7-registro-de-evidencia). Se conservan garantías de [ADR 002](adrs/002-revisions-and-transactions.md).

Concreción de contrato: [diez tools](mcp-contracts.md), [contexto de generación](generation-context.md) y [ADR 007](adrs/007-contracts-and-generation-boundaries.md). Sus DTOs distinguen refs locales de IDs persistidos, input pricing de importes derivados y knowledge revision de progreso/etag editorial.

## 1. Ownership y agregado

V1 usa `user_id = auth.users.id` como tenant físico. El dominio recibe `Principal { userId, actorId, actorKind, clientId?, scopes }`; el agente no elige esos valores. Un actor delegado no crea un usuario catálogo distinto: representa a su dueño autorizado. No hay soporte de equipos ni varias tiendas por comerciante demostrado (E02/E06).

`products` sigue siendo el producto. Agregar `unique (id, user_id)` permite que todo nuevo recurso con `product_id, user_id` tenga FK compuesta a `products(id,user_id) on delete cascade`. Para toda relación entre recursos, usar FK `(related_id, product_id, user_id)` a la clave única equivalente del padre. No basta con validar UUIDs separados. Tablas puente llevan igualmente dueño/producto y sus FKs. RLS SELECT por dueño en tablas visibles; snapshots/receipts/auditoría completos, grants y contextos internos solo por servidor cuando incluyan material que la UI no deba ver directamente. Las escrituras de negocio se reservan a la RPC service_role.

Estados con CHECKs específicos: no reutilizar `content_status` para epistemología. La revisión es única del agregado, nunca un contador por entidad.

FKs de puntero activo se crean diferibles donde hagan falta para evitar ciclos de inserción; ningún `set null` sustituye al borrado completo del producto. Los actores son metadatos de auditoría del dueño, no nuevos tenants.

Para source refs internas, usar unión cerrada de `product_review`, `product_reference_image`, `merchant_note` y assets autorizados. No usar brief/avatar/strategy_run/competitor legacy como fuente implícita del nuevo contexto. Preferir IDs y resolvers existentes, nunca paths locales/URLs firmadas como identidad. Las fuentes conservan el excerpt consultado: si cambia el recurso, no cambia el fragmento histórico. RLS y servicio vuelven a comprobar autorización al resolver la referencia.

## 3. Invariantes y operación transaccional

Una sola familia `lib/product-intelligence/` con schemas puros, policy, services, queries, repository RPC y adapters; types reexportados donde corresponda en `lib/types.ts`. `lib/data/product-intelligence.ts` adapta reads para UI; las diez tools llaman al dominio sin cookies, `redirect()` ni housekeeping. Los HTTP controllers continúan autenticando la UI con `ownedProduct`, pero pasan el principal al mismo servicio.

1. Autenticar/autorizar principal y producto antes de exponer datos. Schema estricto rechaza campos desconocidos, owner/tenant, SQL, paths arbitrarios y valores fuera de límites.
2. Abrir RPC PostgreSQL restringida (`security definer`, search_path fijo, REVOKE public/anon/authenticated, grant service_role explícito). Validadores TypeScript preparan comando; la RPC vuelve a comprobar relaciones, privilegios sensibles, revisión y estado final. El principal solo se construye en el backend autenticado.
3. Bloquear primero el producto/head en orden estable. Resolver primer agregado de forma segura con unique product_id. Consultar el recibo antes del CAS: mismo hash/key devuelve el receipt original aun con revisión posterior; otro hash rechaza. Reservar/confirmar receipt dentro de la transacción; nada de key pendiente fuera de commit.
4. Comparar expected_revision. Resolver client_ref, ejecutar merge/batch, validar todo el grafo final. Archivar dependencia de estrategia activa se rechaza salvo sustitución válida en el batch; como patch no selecciona estrategias en V1, esa sustitución debe ocurrir antes mediante `set_product_strategy`.
5. Diferenciar epistemología de approval. Facts verified requieren evidencia suficiente/revisión documentada; usage approved solo con verify y sin estado disputed/rejected. Proteger también el contenido: cambiar statement/value/unit o respaldo de un fact verified/approved exige verify y nueva revisión documentada; no conservar aprobación al cambiar su afirmación con write normal. La verificación registra hash de contenido/evidencia revisados. Una nueva contradicción conserva el enlace y bloquea uso mediante needs_review hasta resolverla; no desaparece por falta de permiso del actor para aprobar. `observed` requiere source links y `validated` además rationale de validación. No derivarlo de content_status approved.
6. Guardar entidades, nueva revisión, audit, receipt, selección y outbox en una transacción. No escribir proyecciones en fichas/avatares/rankings legacy. Una invalidación de fact/uso marca dependencias `needs_review` mediante relación y evento, sin alterar snapshots históricos. Se rechaza uso futuro hasta revisión. Operación de generación crea su snapshot/request/outbox/receipt atómicos, sin llamada de proveedor dentro del lock.
7. No-op devuelve revisión actual y recibo de éxito sin crear revisión/audit de cambio; log de request puede registrar no-op. `dry_run` valida/diff en snapshot coherente sin persistir entidades ni consumir key. Mantiene CAS, pero no promete reserva hasta solicitud real.

`stale` compara las dependencias congeladas y el contexto operacional vigente; `needs_review` responde a revocación/disputa/bloqueo concreto. Seleccionar con expected=N y based_on=N congela análisis N; el commit pasa cabeza a N+1. Ese incremento por la propia selección no vuelve obsoleta la estrategia inmediatamente: las revisiones de solo lifecycle/selección se excluyen de la comparación de contenido. Un no-op posterior tampoco produce stale.

Contexto/hipótesis/estrategia se editan por MCP; la UI conserva setup, calculadora, assets y revisión de piezas. Ediciones de inputs, precios, etiquetas y fuentes revisadas que afecten al contexto deben entrar al escritor/versionado compartido. Cambios de mercado/políticas invalidan/snapshottean los agregados afectados, con locks ordenados. No activar escritura si queda una ruta que lo bypassa. La finalización del generador guarda output asociado a su snapshot y no reemplaza automáticamente material revisado/selección más reciente.

## 4. Oferta, ejecución e identidad de ángulos

Los precios operativos continúan en `product_pricing` y se calculan con `suggestPrices/buildPricingPlan` (E17; `lib/pricing/plan.ts:104`). Se conserva `PricingSection` (`components/screens/pricing-section.tsx:53`): costo del proveedor obligatorio, supuestos actuales y precio/tachado efectivos editables. `save_product_context` recibe datos básicos y, si se envían, inputs del formulario; el mismo servicio completa cálculos con defaults válidos y exige supuestos faltantes. La UI sigue siendo una vía de configuración validada. En get_product_context se devuelve el plan guardado y su stamp; el chat no calcula ni sobrescribe derivados.

pi_offers guarda snapshot de la oferta calculada más enfoque/etiquetas propuestas. Guardar un análisis parcial no exige pricing listo; generar/publicar sí. Condiciones opcionales unknown simplemente no se afirman. Cambios de precios invalidan oferta/etiquetas y marcan estrategias stale sin cambiar Shopify automáticamente. La revisión de etiquetas se mantiene en la calculadora; sus propuestas nuevas llegan del chat y no del cliente ideal generado.

Snapshot V1 implementado en dominio: una persona principal por decisión; todos los ángulos secundarios corresponden a ella. `related_jtbd`, `related_pains` y `desires` cierran referencias adicionales junto con hechos/fuentes/evidencia/objeciones/lenguaje. El análisis completo conserva múltiples personas. Una estrategia que mezcle personas necesita una extensión explícita de snapshot antes de habilitarla.

Contrato Offer utiliza enteros en unidad menor para importes cobrables; el adaptador convierte los `numeric` existentes con decimal exacto y escala monetaria validada para la tienda, comprobando safe integer. Ganancia/CPA máximo/precio promedio por unidad son métricas analíticas y el DTO los conserva como decimales en unidad mayor, sin forzar sus fracciones a precio cobrable. No usar directamente `currencyMinorUnitFactor` de Meta: es un contrato específico de Meta (p. ej. COP) y su `Math.round` puede esconder datos inválidos. Snapshot registra escala y precio original; preservar null en costo/condiciones desconocidos.

Selección primaria existe para get_product_strategy y nunca se infiere de slot=1. UGC/landing nuevos consumen directamente el contexto MCP; se retira la exigencia legacy de dos/tres desarrollos para estas salidas. Un UGC puede usar un angle_id válido; landing puede usar los seleccionados según su brief. Slots se conservan solo como agrupación operativa donde Meta los necesite. Su mapping a IDs canónicos se congela por campaña/operación; no cambia identidad ni reetiqueta medios/campañas antiguos.

| `generate_ugc` | `requestUgc` | angle_id estable, etapa script/keyframes/clips, refs autorizadas y revisión previa requerida. Snapshot, guards de proveedor y job; no exigir filas legacy aprobadas. |
| `get_generation_status` | `getGenerationStatus` | Lectura autorizada de operación/run/outputs/coste y siguiente revisión. No dispara sync, polling externo ni housekeeping. |

Ampliar include del contexto con context/pricing/setup y missing_fields; en lectura de producto no inicializado devolver conocimiento/selección vacíos, catálogo/pricing operativos con su fecha y revision=0, sin escribir ni importar análisis. Offer editable admite selección de packs disponibles, enfoque y etiquetas propuestas; importes/ganancias/CPA/condiciones operativas se derivan o referencian y no se aceptan como números autoritativos enviados por el chat. Nuevos schemas explicitan estos campos y los targets/etapas de generación antes de implementar.

Knowledge/setup/selección producen revisión si cambian el agregado. Solicitar generación verifica expected_revision y congela esa revisión sin incrementar el análisis por crear un job; sus estados/progreso tienen identidad y control de concurrencia operacionales propios. Dos pedidos de UGC/landing pueden usar N sin hacerse stale entre sí; editar conocimiento a N+1 no modifica sus inputs. El receipt de generación guarda operation_id, no una respuesta que pretenda que el render ya terminó.

Provenance en runs/medios se agrega de forma aditiva. Para video_scripts nuevos, angle_id canónico y strategy/revision sustituyen la identidad por angle_slot; ajustar nullability/índice de activo por producto/angle_id/formato sin reinterpretar filas anteriores. Para Meta, angle_slot y angles_stamp antiguos se conservan en campañas/medios existentes; agregar refs canónicas en nuevos recursos y mapping de variante por campaña. Nunca asignar angle_id a datos antiguos por similitud de texto o índice.

Prioridades contiguas por conjunto: personas y ofertas del producto; JTBD/pains/desires/objections/angles por persona. Language no tiene prioridad en el spec, por lo que reprioritize language se rechaza. Un create/update con prioridad desplaza/reindexa el conjunto de forma determinista; reprioritize exige todos los IDs activos del conjunto. Refs locales son únicas globalmente dentro de la llamada, independientes de orden de arrays. Duplicate IDs/client_ref u operaciones contradictorias sobre el mismo ID se rechazan con detalles, no se elige arbitrariamente el último.

Límites iniciales del spec: request 256 KiB, respuesta 128 KiB, campo 8 KiB, colección de entrada 100, batch 50, timeout 15 s. No hay límite implícito de 100 entidades totales guardadas; por eso lecturas paginan por presupuesto de bytes además de page_size. `view=summary` no cambia veracidad ni oculta una referencia necesaria; informa conteos, truncated y cursor. Rate limit y tamaño de agregado se medirán en fixtures/piloto.

Cursor firmado liga actor/tenant/product/revision/include/view/include_archived/última posición/expiry. La parte de inteligencia siempre sale del snapshot inmutable; los summaries auxiliares se capturan una vez en `pi_context_reads` con `execution_as_of` explícito. Para at_revision sin provenance histórica de PDP/asset/performance, devolver unknown/no snapshot + warning, no el estado vivo como si perteneciera a esa revisión. Verificación/uso vigente se devuelve separada de los hechos históricos: revocar un claim bloquea su uso hoy aunque una lectura histórica lo muestre aprobado entonces. Fuentes/copy se marcan como datos no confiables, nunca instrucciones.

|---|---|---|

V1 incorpora setup y generación, por lo que provenance de runs/medios y pi_generation_requests se implementan en esa entrega. PDPVersion completo, PublishOperation nuevo, experiments, observations y learnings quedan después; no se recrean módulos de Meta. Toda relación y asset nuevo entra al borrado central. Las migraciones se validan en entorno aislado antes de aplicar a datos reales.

## Adiciones implementadas para el cierre

`pi_product_learnings`: UUID, product/user, revisión única por producto, strategy_id, ventana de medición, contenido del chat, performance congelada, actor y fecha. Inmutable, lectura del dueño, FK compuesta hacia el agregado y FK de estrategia con cascada. Puede citarse como fuente interna `product_learning`.

`pi_gallery_operations`: UUID, product/user, identidad delegada para reautorización interna, huella de contexto, UUID de imagen base congelado, coste estimado, QA, estado y timestamps. RLS sin SELECT del cliente: la consulta autorizada de estado proyecta solo datos públicos de la operación. `page_images.pi_operation_id` enlaza la cola con cascada. El UUID base es snapshot sin FK hacia la referencia: borrar una referencia no debe borrar assets antes de limpiar Storage.

`event_copy.provenance` y `ad_media.content_provenance` conservan autoría/contexto y selectores. Los inputs de runs guardan estrategia, pricing, hechos verificados y huella/base de generación. `products.usage_tip` añade source/status/provenance/revisiones de hechos aprobados. Ningún valor de estado UI en español se persiste.

El resto reutiliza entidades operativas. Nombre/descripción/proveedor van a `pi_product_inputs` por el writer canónico, sin seguir escribiendo `products.product_data`/`base_info`. No se importan avatares ni ángulos legacy al modelo PI. [ADR 016](adrs/016-chat-content-learning-and-render.md).
